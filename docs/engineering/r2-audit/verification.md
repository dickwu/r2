# Performance and reliability audit: implementation and acceptance

Baseline: `f81deec37488b5dcf79b0518ead3cad0263e79d0`. `validation.json` records a local snapshot captured on 2026-09-12 against that baseline with uncommitted changes on top; it is not bound to the current git tree and its command outcomes should not be read as current.

Acceptance status is now generated from `acceptance-manifest.json` into `acceptance-status.json` and `acceptance-status.md`. The generated status records exact git commit/tree, dirty state, platform, the shared production-source fingerprint, harness hashes, evidence hashes, provider versions/commits and execution mode. `scripts/audit-source.mjs --json` is the side-effect-free API for build records; it hashes production inputs under `src/**`, `src-tauri/src/**`, `src-tauri/crates/**`, Tauri capabilities/icons, Cargo manifests/locks, and frontend build configs, while excluding docs, scripts, generated evidence/status and build outputs. Update the manifest or evidence files, then run `node scripts/r2-audit-manifest.mjs --write`; do not hand-edit generated status. The provider harnesses (`scripts/native-rustfs-audit.mjs`, `scripts/r2-protocol-audit.mjs`, `scripts/aws-s3-protocol-audit.mjs`) record `git.{commit,tree,dirty}` and `source_fingerprint` when they create a report (`auditProvenance` in `scripts/audit-source.mjs`), and a gate with `require_current_git` reads `passed` only when the generator runs at that same commit and tree with nothing uncommitted on either side except evidence and generated status under `docs/engineering/r2-audit/`; the manifest and this file (`verification.md`) are not exempt. So run a harness from a clean checkout, regenerate the status before committing its evidence, and commit both together; the generated status then records the parent of the commit that carries it. A dirty worktree, absent or null git metadata, or evidence without a git field all downgrade to `historical_*` with a reason that says which.

**Overall acceptance remains incomplete.** The implementation and local tests below do not establish real AWS/R2 compatibility, Linux/Windows native behavior, power-loss durability, or production throughput. Those requirements remain open rather than being replaced by fixture results.

The opt-in macOS NFS test and normal debug desktop build also passed at capture time; `validation.json` also records the React Doctor command outcome from that capture, whose score and warning counts are point-in-time and are not restated here. Evidence artifacts:

- `native-ipc-recovery.json`: real Tauri IPC and SQLite across app restart, backed by two local HTTP fixtures. Source DELETE is denied initially; after credential refresh, recovery deletes the source with exactly one source GET and one destination PUT overall. This is not a real provider deployment.
- `listing-benchmark.json`: ten runs each at 10,000 and 100,000 items through production merge/cache helpers. Excludes S3, SQLite, IPC, React rendering and OS mount latency. - `acceptance-status.json` / `acceptance-status.md`: generated manifest status. ## Safety and compatibility decisions

- Destination overwrite is rejected for application Move. A same-key request is handled by the backend; UI checks are supplementary.
- If a provider cannot enforce required conditional mutation, the source or dirty stage is retained and the operation reports that it needs attention. Capability probes touch only unique `.r2-operation-checks/` keys with separate cleanup budgets. Unsupported capability is a product limitation, not a successful mutation.
- Uncertain completion is reconciled against recorded identity and, when the receipt is missing, matching content. A HEAD 404 alone does not prove a dispatched write can never commit. Replays use the original persisted precondition.
- A transient capability outage does not permanently pause a stage. Unsupported rename capability is rejected before a new rename journal freezes affected files. Existing uncertain journals remain recoverable.
- Stable NFS WRITE acknowledgment follows local file/write-intent/manifest synchronization. It does not promise that remote S3 publication has completed. Recovery folders are retained across unsuccessful drain/unmount.
- Large relay parts may reserve substantial temporary disk space. The 256 MiB buffer budget and stage quota protect separate resources and are not a whole-process memory guarantee.

## Open acceptance requirements

1. Real AWS and Cloudflare R2 testing with dedicated buckets. Include versioning, permission expiry, unknown Complete/Delete responses, and actual large-object transfer. The R2 and AWS harnesses are prepared but not executed against external buckets unless explicit isolated `R2_AUDIT_*` or `AWS_AUDIT_*` inputs are supplied. AWS now requires explicit `AWS_AUDIT_SOURCE_BUCKET` and `AWS_AUDIT_DEST_BUCKET`; equal values run the same-bucket matrix and distinct values run the cross-bucket matrix. AWS response-loss uses a client-side request-handler wrapper that forwards the genuine Complete/Delete request once, drains the provider response, throws `InjectedResponseLoss`, and then reconciles by independent HEAD/Get evidence; this wrapper's request/response handling was exercised once against a disposable local RustFS instance during development, not against AWS or R2, and has not been re-verified since. That loopback mode (`--local-response-loss-test`) writes its report to `.omx/artifacts/aws-protocol/local-<owner>.json` marked `local_fixture: true` / `provider_kind: "local-rustfs"` with the fixture endpoint; the `aws-s3-provider` gate requires `local_fixture == false` and `provider_kind == "aws"`, so such a report can never be read as AWS acceptance evidence.
2. Linux and Windows native mount/read/write/rename/delete/recovery tests with preserved evidence artifacts. Existing preview CI compiles Windows tests with `--no-run` and runs Windows NFS `--validate-only`, so a green preview build alone cannot close Windows behavior acceptance. A separate windows-2022 behavioral workflow (`.github/workflows/windows-native.yml`) is listed as prepared/unrun until it is dispatched and preserves evidence. To land a run: download the `windows-native-nfs-behavior` artifact from that workflow run, copy its `windows-native-nfs-behavior.json` to `docs/engineering/r2-audit/`, and run `node scripts/r2-audit-manifest.mjs --write`; the `windows-native-nfs-behavior` gate then requires `status == observations_collected`, `native_nfs.write_read_rename_unmount == passed`, SDK `10.0.19041.0`, runner `windows-2022`, and a `source_fingerprint.production_source_sha256` matching the tree being evaluated (the workflow captures it right after checkout, so only a run of the same production source can close the gate).
3. A power-loss/VM crash experiment at the stable NFS acknowledgment boundary, busy/unresponsive mount teardown, and long weak-network fault scenarios. `scripts/provider-fault-audit.mjs --execute` now records SDK/proxy-level 503/outage/Retry-After/body-stall/cancel checks against a disposable provider. `--execute-app` is a separate current-app runner for Move task outage/restart/resume/cancel evidence plus native NFS outage/recovery evidence. It requires a freshly built isolated audit binary and matching `build.json`; the report records that build snapshot, current production-source fingerprint including untracked source files, source tree fingerprints and app binary hashes before/after the run. Smoke mode defaults to a 10-second app outage; acceptance mode defaults to five minutes. The NFS subcheck mounts through the app, stages a write during source outage, verifies dirty/pending state and absent remote object, restores the source and waits for digest convergence, then stops/restarts the app to verify retained recovery inventory and recovered remote digest with no post-stop proxy dispatch. Direct move-journal `next_attempt_at`/phase/source inspection still is not exposed through production IPC. Power-loss is prepared through `scripts/vm-powerloss-audit.py` plus the disposable VM runner and guest tests, and remains unexecuted for production acceptance until the VM matrix is actually run in a disposable environment with the elevated guest access it requires. The offline CI self-test validates recovery-result guards without controlling a VM.
4. Complete native end-to-end performance measurements: interactive startup, first visible page, warm navigation p50/p95, queue/network/DB/IPC/sort breakdown, requests per object/MiB, throughput/retransmitted bytes, peak in-flight buffers/RSS, connection reuse, dirty-byte age, recovery convergence and post-cancel requests.
5. Targeted NFS LOOKUP acceptance: an unknown child name still resolves through a full directory materialization (`directory_view(...all=true)`) rather than a direct HEAD/prefix probe or an already-published positive-child fast path. READDIR paging is already incremental (see F10 above); point lookups have not been separately measured or accepted at scale, and closing that gap does not require changing the READDIR path.
6. RustFS deployment compatibility beyond the already-passed exact-version loopback evidence: real large-object transfers, long provider outages and recovery, and capability behavior verified both before and after a RustFS version upgrade.

These requirements stay open until they are verified against the current source and recorded as generated gate evidence. This document makes no production-readiness claim beyond what the generated `acceptance-status.json`/`.md` show for the commit being evaluated.
