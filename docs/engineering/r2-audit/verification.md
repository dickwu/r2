# Performance and reliability audit: implementation and acceptance

Baseline: `f81deec37488b5dcf79b0518ead3cad0263e79d0`, version 0.3.4. Work date: 2026-09-12. This implementation is being prepared on an audit review branch; no release or production deployment has been made. `validation.json` records the local snapshot at the time its checks ran.

Acceptance status is now generated from `acceptance-manifest.json` into `acceptance-status.json` and `acceptance-status.md`. The generated status records exact git commit/tree, dirty state, platform, the shared production-source fingerprint, harness hashes, evidence hashes, provider versions/commits and execution mode. `scripts/audit-source.mjs --json` is the side-effect-free API for build records; it hashes production inputs under `src/**`, `src-tauri/src/**`, `src-tauri/crates/**`, Tauri capabilities/icons, Cargo manifests/locks, and frontend build configs, while excluding docs, scripts, generated evidence/status and build outputs. Update the manifest or evidence files, then run `node scripts/r2-audit-manifest.mjs --write`; do not hand-edit generated status.

**Overall acceptance remains incomplete.** The implementation and local tests below do not establish real AWS/R2 compatibility, Linux/Windows native behavior, power-loss durability, or production throughput. Those requirements remain open rather than being replaced by fixture results.

## Safety and compatibility decisions

- Destination overwrite is rejected for application Move. A same-key request is handled by the backend; UI checks are supplementary.
- If a provider cannot enforce required conditional mutation, the source or dirty stage is retained and the operation reports that it needs attention. Capability probes touch only unique `.r2-operation-checks/` keys with separate cleanup budgets. Unsupported capability is a product limitation, not a successful mutation.
- Uncertain completion is reconciled against recorded identity and, when the receipt is missing, matching content. A HEAD 404 alone does not prove a dispatched write can never commit. Replays use the original persisted precondition.
- A transient capability outage does not permanently pause a stage. Unsupported rename capability is rejected before a new rename journal freezes affected files. Existing uncertain journals remain recoverable.
- Stable NFS WRITE acknowledgment follows local file/write-intent/manifest synchronization. It does not promise that remote S3 publication has completed. Recovery folders are retained across unsuccessful drain/unmount.
- Large relay parts may reserve substantial temporary disk space. The 256 MiB buffer budget and stage quota protect separate resources and are not a whole-process memory guarantee.

## Open acceptance requirements

1. Real AWS and Cloudflare R2 testing with dedicated buckets. Include versioning, permission expiry, unknown Complete/Delete responses, and actual large-object transfer. The R2 and AWS harnesses are prepared but not executed against external buckets unless explicit isolated `R2_AUDIT_*` or `AWS_AUDIT_*` inputs are supplied. AWS now requires explicit `AWS_AUDIT_SOURCE_BUCKET` and `AWS_AUDIT_DEST_BUCKET`; equal values run the same-bucket matrix and distinct values run the cross-bucket matrix. AWS response-loss uses a client-side request-handler wrapper that forwards the genuine Complete/Delete request once, drains the provider response, throws `InjectedResponseLoss`, and then reconciles by independent HEAD/Get evidence; this wrapper has been proven against disposable local RustFS.
2. Linux and Windows native mount/read/write/rename/delete/recovery tests with preserved evidence artifacts. Existing preview CI compiles Windows tests with `--no-run` and runs Windows NFS `--validate-only`, so a green preview build alone cannot close Windows behavior acceptance. A separate windows-2022 behavioral workflow is listed as prepared/unrun until it is dispatched and preserves evidence.
3. A power-loss/VM crash experiment at the stable NFS acknowledgment boundary, busy/unresponsive mount teardown, and long weak-network fault scenarios. `scripts/provider-fault-audit.mjs --execute` now records SDK/proxy-level 503/outage/Retry-After/body-stall/cancel checks against a disposable provider. `--execute-app` is a separate current-app runner for Move task outage/restart/resume/cancel evidence plus native NFS outage/recovery evidence. It requires a freshly built isolated audit binary and matching `build.json`; the report records that build snapshot, current production-source fingerprint including untracked source files, source tree fingerprints and app binary hashes before/after the run. Smoke mode defaults to a 10-second app outage; acceptance mode defaults to five minutes. The NFS subcheck mounts through the app, stages a write during source outage, verifies dirty/pending state and absent remote object, restores the source and waits for digest convergence, then stops/restarts the app to verify retained recovery inventory and recovered remote digest with no post-stop proxy dispatch. Direct move-journal `next_attempt_at`/phase/source inspection still is not exposed through production IPC. Power-loss is prepared through `scripts/vm-powerloss-audit.py` plus the disposable VM runner and guest tests, and is still unexecuted for production acceptance until root runs the VM matrix. The offline CI self-test validates recovery-result guards without controlling a VM.
4. Complete native end-to-end performance measurements: interactive startup, first visible page, warm navigation p50/p95, queue/network/DB/IPC/sort breakdown, requests per object/MiB, throughput/retransmitted bytes, peak in-flight buffers/RSS, connection reuse, dirty-byte age, recovery convergence and post-cancel requests.
5. Incremental NFS directory generations/cookies if the full-directory first READDIR cost is to be removed. UI first-page streaming and NFS singleflight are already separate implementations.

The goal must stay incomplete until these requirements are either verified or explicitly changed by the user. The user subsequently authorized full deployment and local installation after completion; the delivery sequence is recorded in the implementation plan. Publication and installation have not yet been performed, and this report makes no production-readiness claim.
